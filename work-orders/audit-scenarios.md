## 공통 지시

> 세 명 모두

### 시작하기

1. 저장소를 받고 README의 **"처음 시작하기"**를 그대로 따라 합니다(uv, MongoDB, Foundry 설치 → 서브모듈 → `uv sync` → `.env.local`). 화면을 볼 때만 Node 22와 `web/`의 `npm install`이 필요합니다.
2. README의 **"감사 규칙 추가하기"**와 **"테스트가 확인하는 것"**을 먼저 읽습니다. 규칙을 꽂는 방법과 예시 코드가 있습니다.
3. main에서 자기 브랜치를 만듭니다: `feat/audit-limit`(1번), `feat/audit-replay`(2번), `feat/audit-budget`(3번).
4. TypeScript판(PBL-Aegis/agent-M2M)에서 이미 작업한 내용이 있으면, Solidity 파일(`contracts/src/rules/`, `contracts/test/`)은 그대로 옮겨 오고 서버 규칙·서버 테스트만 Python으로 다시 씁니다.

```bash
git clone <Python 서버판 저장소 주소> agent-M2M-py
cd agent-M2M-py
git submodule update --init --recursive
uv sync
cp .env.example .env.local
```

### 코드 쓰는 곳

| 무엇 | 어디에 | 함께 쓰는 파일에 추가할 것 |
| --- | --- | --- |
| 서버 규칙 | `agent_m2m/rules/<이름>.py` (새 파일) | `agent_m2m/rules/__init__.py`에 `from agent_m2m.rules import <이름>  # noqa: F401` 한 줄 |
| Solidity 규칙 | `contracts/src/rules/<이름>Rule.sol` (새 파일) | `contracts/src/AegisToken.sol` 두 군데에 내 규칙 이름: ① `contract AegisToken is …,` 뒤 ② `override(…)` 괄호 안. 예시는 README "감사 규칙 추가하기" |
| 서버 테스트 | `tests/test_<이름>.py` (새 파일) | 없음 |
| Solidity 테스트 | `contracts/test/<이름>Rule.t.sol` (새 파일) | 없음 |
| 새 저장소가 필요할 때 | 규칙 파일 안에서 `agent_m2m.store.database()["<컬렉션 이름>"]`로 새 컬렉션을 씀 | 없음 |

### 지켜야 할 것

- `agent_m2m/purchase.py`, `audit.py`, `payment.py`, `selection.py`, `api.py`와 다른 사람의 규칙 파일은 고치지 않습니다. 꼭 필요하면 먼저 말해 주세요.
- **토큰은 따로 배포하거나 발급하지 않습니다.** `uv run python scripts/local_chain.py`(이하 "로컬 체인")를 켜면 자기 컴퓨터 안의 가짜 체인에 AEGIS 토큰(자기 규칙이 들어간 최신 코드)이 자동으로 배포되고, 구매자 지갑에 1000 AEGIS가 들어옵니다. 잔액은 사람마다 따로이고, 끄면 사라지고, 다시 켜면 1000 AEGIS로 초기화됩니다. Base Sepolia 배포는 세 규칙을 모두 합친 뒤 한 번만 하며 팀원이 할 일이 아닙니다.
- 직접 실행할 때도, 자동 테스트(`uv run pytest`)도 결제는 `local`(가짜 체인)로 진짜 체인에 나갑니다. `uv run pytest`는 테스트용 가짜 체인을 스스로 켜고 끄니 따로 할 일은 없습니다. Base Sepolia(`live`)는 켜지 않습니다.
- 요청을 보낼 때는 우선순위(`price`·`speed`·`intelligence`)를 넣어서 보냅니다. 그러면 Qwen(Ollama)이 없어도 됩니다.
- 모델 이름이나 금액을 코드·테스트에 박아 넣지 않습니다. 판매 모델 목록은 바뀔 수 있습니다. 금액은 `ctx.decision["winner"]["amountUnits"]`에서 읽습니다. **사람이 적는 금액(설정값, 문서)은 AEGIS로 씁니다**(1 AEGIS = 1달러). 코드 안에서는 units(1 AEGIS = 1,000,000 units)로 바꿔 계산합니다. units가 있는 이유: 블록체인은 소수점을 저장할 수 없어서 토큰 금액을 정수로만 셉니다. 그래서 체인과 코드 안에서는 0.16 AEGIS를 160000 units로 다룹니다(은행이 달러를 센트로 다루는 것과 같고, USDC도 같은 방식). 사람이 units를 직접 적을 일은 없게 합니다.
- 요청 두 개가 거의 동시에 오면, 둘 다 "아직 한도 안 넘었네"라고 보고 둘 다 통과할 수 있습니다. 그래서 **"확인"과 "기록"을 DB 명령 하나로 같이** 하세요. 예: `find_one_and_update`(조건이 맞을 때만 바꾸기), unique index(같은 값 두 번 저장 금지). 파이썬 변수에 잠금(`threading.Lock`)을 거는 방식은 서버가 여러 대면 통하지 않아서 쓰지 않습니다.
- 체인에서는 구매자 지갑(`from`) 하나를 사용자 한 명으로 봅니다.
- Solidity 테스트에서는 테스트 파일 안에 **"AEGIS + 내 규칙만" 붙인 작은 토큰을 따로 정의해서** 시험합니다(`contracts/test/AegisToken.t.sol`의 `RuledToken` 예시처럼, 코드 몇 줄). 실제로 토큰을 발급하거나 배포하는 게 아니라, `forge test`가 돌 때마다 메모리 안의 가짜 체인에 잠깐 올렸다 버리는 것입니다. 이렇게 하는 이유는, 세 규칙이 진짜 토큰에 합쳐지면 서로 걸리기 때문입니다. 예를 들어 1번의 "10건 연속 결제" 테스트가 2번의 "60초에 5건" 규칙에 먼저 막혀 1번 규칙을 확인할 수 없게 됩니다. "하루 지나면 초기화" 같은 시간 테스트는 `vm.warp`(테스트 안에서 시계를 앞으로 돌리는 기능)로 합니다.
- 서버 테스트(`uv run pytest`)는 결제가 테스트용 가짜 체인에 진짜로 나가고, **세 사람의 체인 규칙이 모두 들어간 진짜 토큰**을 거칩니다. 그래서 이렇게 짭니다.
  - 테스트마다 체인이 처음 상태(구매자 1000 AEGIS, 한도·요청 번호 기록 없음)로 자동으로 돌아갑니다. 한 테스트 안에서는 결제가 쌓입니다. 따로 할 일은 없습니다.
  - 체인 시계를 돌려야 하면 `tests/helpers.py`의 `increase_chain_time(초)`를 씁니다.
  - 서버 쪽 기록(MongoDB)은 한 테스트 파일 안에서 이어지므로, 테스트마다 다른 `userId`·`requestId`를 씁니다.
  - "몇 건 성공했나"보다 **"내 규칙 이름으로 막혔나"**(차단 알림의 `rule`, 실패 이유)를 확인합니다. 한 테스트에서 6건 넘게 보내면 다른 사람의 "60초에 5건" 체인 규칙에 먼저 걸릴 수 있기 때문입니다.

### 숫자는 설정값(변수)으로

아래 시나리오 표의 **기본값**(0.5 AEGIS, 3 AEGIS, 60초에 5건 등)은 처음 시작할 값일 뿐이고, 나중에 바뀔 수 있습니다. 코드에 숫자를 직접 쓰지 말고 이름 붙은 설정값으로 둡니다.

- **서버**: 규칙 파일 맨 위에 이름 붙은 상수로 두고, 같은 이름의 환경변수로 바꿀 수 있게 합니다. **금액 설정값은 AEGIS로 받고, 코드에서 `parse_aegis`(`agent_m2m/format.py`)로 units로 바꿉니다.** 예: `LIMIT_PER_DAY_UNITS = parse_aegis(os.environ.get("AUDIT_LIMIT_PER_DAY", "3"))`. 테스트에서 값을 바꿀 때는 `monkeypatch.setattr(규칙모듈, "LIMIT_PER_DAY_UNITS", ...)`을 씁니다(규칙 파일을 다시 불러오면 규칙이 두 번 등록됩니다). 새 환경변수는 `.env.example`에 기본값과 한 줄 설명을 추가합니다(함께 쓰는 파일이라 자기 줄만 더합니다).
- **체인(Solidity)**: 규칙 컨트랙트의 상태 변수로 두고 기본값은 서버와 같게 합니다. 바꾸는 함수는 **운영자(`owner`)만** 부를 수 있게 합니다(규칙 컨트랙트가 OpenZeppelin `Ownable`을 상속하면 `onlyOwner`를 쓸 수 있습니다). 체인 컨트랙트는 배포 후 코드를 고칠 수 없어서, 값만 바꿀 수 있게 해 두는 것입니다. 체인은 소수점을 못 다루므로 컨트랙트 안의 금액은 units로 둡니다(예: 0.5 AEGIS = `500000`).
- **서버와 체인의 기본값은 같게** 둡니다. 한쪽을 바꾸면 다른 쪽도 바꿉니다.
- **테스트도 숫자를 직접 쓰지 않고** 같은 설정값에서 계산합니다. 예: "몇 번째 결제부터 막히나" = 하루 상한 ÷ 한 건 금액을 넘는 첫 번째.
- 변수로 두지 않는 것(규칙 자체): "하루 = UTC 자정 기준", "요청 번호당 1번", "구매자 예산 설정값이 비어 있으면 통과".

## 시나리오 1 · 한도 쪼개기

> 1번 담당

**한 줄 요약:** 하루 3 AEGIS를 넘는 결제를 서버와 체인에서 막고, "10건 동시 결제" 테스트로 증명하기.

> **공격:** 0.4 AEGIS짜리 결제를 1분 안에 10건 동시에 보내서, 하루 한도 3 AEGIS를 넘깁니다. 한 건씩 보면 한도 안이라 걸리지 않는 점을 노립니다.

### 막을 것

| 검사 | 서버 | Solidity | 기본값 (설정값 이름) | 걸리면 |
| --- | --- | --- | --- | --- |
| 1건 상한 | ✔ 송금 직전 자리 | ✔ | 0.5 AEGIS (`AUDIT_LIMIT_PER_PAYMENT` = 0.5) | 결제 거절 |
| 하루 상한 | ✔ 송금 직전 자리, 예약 방식(아래) | ✔ | 3 AEGIS (`AUDIT_LIMIT_PER_DAY` = 3), UTC 날짜 기준, 사용자별 | 결제 거절 |
| 동시 요청 틈 | ✔ 확인과 예약을 DB 명령 하나로 | 체인이 순서대로 처리 | - | 한도를 넘는 순간부터 거절 |
| 한도 임박 알림 | ✔ | ✘ | 하루 한도의 80% (`AUDIT_LIMIT_WARN_RATIO` = 0.8) | 결제는 진행, 알림 |
| 쪼개기 패턴 탐지 | ✔ | ✘ | 1건 상한의 80% 이상(`AUDIT_SPLIT_MIN_RATIO` = 0.8) 결제가 10분 안에(`AUDIT_SPLIT_WINDOW_SECONDS` = 600) 3건(`AUDIT_SPLIT_COUNT` = 3) | 알림 |
| 송금 전 실패 시 되돌리기 | ✔ 결제 후 자리 | 실패하면 자동 취소 | - | 예약한 금액 복구 |

**예약 방식**이란, 송금하기 전에 오늘 쓴 금액에 이번 금액을 **먼저 더해 두는 것**입니다. 더했는데 3 AEGIS를 넘으면 바로 거절하고, 송금이 실패하면 나중에 다시 빼 줍니다. 이렇게 해야 10건이 동시에 와도 한도를 넘지 않습니다.

### 쓸 자리

- **서버** `BEFORE_PAYMENT_CHECKS`: 1건 상한, 하루 상한 예약, 80% 알림, 쪼개기 탐지
- **서버** `AFTER_PAYMENT_CHECKS`: `record["status"] == "FAILED"`이고 `record.get("failureStage") == "before-send"`면 예약한 금액을 되돌림
- **Solidity** `LimitRule`: 1건 상한, 지갑(`from`)별 하루 합계. "오늘"은 체인의 현재 시각을 하루(86,400초)로 나눈 몫(`block.timestamp / 1 days`)으로 정하고, 이 값이 바뀌면 합계를 0부터 다시 셉니다(UTC 자정 기준).

### 재현 테스트

- 서버: 같은 사용자로 0.4 AEGIS 결제를 10건 동시에(`ThreadPoolExecutor`) 보내, 하루 상한을 넘는 결제부터 **내 규칙(한도) 이름으로** 막히는지 확인합니다(기본값이면 0.4 × 7 = 2.8, 8번째가 3.2라 8번째부터. 몇 번째인지는 설정값에서 계산). 2번 담당의 "60초에 5건" 체인 규칙이 합쳐지면 6·7번째가 체인에서 먼저 실패할 수 있으니, 성공 개수 대신 한도 규칙의 차단 알림 개수(3건)를 확인합니다. 금액은 `maxOutputTokens`로 맞춥니다.
- 서버: 송금 전에 실패한 건의 예약이 되돌려져 한도가 다시 생기는지 확인합니다.
- Solidity: 같은 지갑으로 `pay(…, 400000, …)`를 10번 불러 8번째부터 revert 되는지, 600000 한 번은 바로 revert 되는지 확인합니다.

## 시나리오 2 · 재시도·재전송

> 2번 담당

**한 줄 요약:** 같은 요청 번호는 한 번만 결제되게 서버와 체인에서 막고, "같은 번호로 두 번·동시에 보내기" 테스트로 증명하기.

> **공격(실수):** 응답이 늦자 요청 프로그램이나 SDK가 같은 요청을 다시 보내서, 같은 구매가 여러 번 결제됩니다.

### 막을 것

| 검사 | 서버 | Solidity | 기본값 (설정값 이름) | 걸리면 |
| --- | --- | --- | --- | --- |
| 같은 요청 번호 재결제 | ✔ 상태표대로 | ✔ | 요청 번호당 1번 | 아래 상태표 / 체인에서 거절 |
| 같은 번호 동시 도착 | ✔ 하나만 처리 | 순서대로 처리돼 두 번째 거절 | - | 나머지는 "처리 중"(409) |
| 짧은 시간 결제 횟수 | ✘ | ✔ | 60초에 5건, 지갑별 (체인 `rateWindow` = 60, `rateLimit` = 5) | 결제 거절 |
| 같은 문장 반복 | ✔ | ✘ (문장을 모름) | 같은 문장 60초에(`AUDIT_REPEAT_WINDOW_SECONDS` = 60) 3번(`AUDIT_REPEAT_COUNT` = 3) | 멈추고 사용자 확인(409) |
| 요청 번호 보관 기간 | ✔ | 영구 | 서버 24시간 (`AUDIT_REQUEST_ID_TTL_SECONDS` = 86400) | 지나면 새 요청으로 봄 |

### 같은 요청 번호로 다시 왔을 때 (상태표)

| 첫 요청의 상태 | 서버 처리 |
| --- | --- |
| 처리 중 (`PROCESSING`) | "처리 중"이라고 답하고 막음 (409) |
| 성공 (`SETTLED`) | 새로 결제하지 않고 이전 기록을 그대로 돌려줌 |
| 송금 전 실패 (`FAILED`·`before-send`) | 다시 처리 |
| 송금 후 실패 (`FAILED`·`after-send`) | 멈추고 사용자 확인 (409). 이중 결제 위험 |

### 쓸 자리

- **서버** `ON_REQUEST_CHECKS`: 상태표 처리, 같은 번호 동시 도착, 같은 문장 반복.
  - 이미 성공한 요청이 다시 오면, 규칙 함수에서 **그때의 구매 기록을 그대로 돌려주세요**(`return store.get_purchase(...)`). 서버가 새로 결제하지 않고 그 기록을 응답으로 보냅니다. 요청 번호는 이미 구매 기록의 `requestId`에 남습니다.
  - 동시 도착: 요청 번호만 모아 두는 표(컬렉션)를 새로 만들고, **같은 번호는 두 번 못 넣게** 설정하세요(unique index). 먼저 넣은 쪽만 처리하고, 넣기에 실패한 쪽은 "처리 중"(409)으로 답합니다. 이 표의 기록은 **`AUDIT_REQUEST_ID_TTL_SECONDS`(기본 24시간) 뒤 자동으로 지워지게** 하세요(TTL index, `expireAfterSeconds`).
- **Solidity** `ReplayRule`: 쓴 `requestId` 기록(같은 번호는 revert), 지갑별 60초 5건 제한

### 재현 테스트

- 서버: 같은 `requestId`로 두 번 차례로 보내면 두 번째가 같은 기록(같은 `id`)을 돌려받고 결제는 1번인지 확인합니다.
- 서버: 같은 `requestId`로 동시에 두 번 보내면 하나만 `SETTLED`, 나머지는 409인지 확인합니다.
- 서버: 송금 전 실패 뒤 같은 번호는 다시 처리되고, 송금 후 실패 뒤 같은 번호는 409인지 확인합니다.
- Solidity: 같은 `requestId`로 `pay` 두 번이면 두 번째가 revert, 60초 안에 6번째 결제가 revert 되는지 확인합니다.

## 시나리오 3 · 요청 바꿔치기

> 3번 담당

**한 줄 요약:** 구매자의 한 건 예산(설정값)보다 비싼 결제를 막고, "같은 요청의 우선순위만 바꿔 보내기" 테스트로 증명하기.

> **공격(해킹 가정):** 사용자 쪽 요청 프로그램이 해킹돼서, 사용자가 고른 "싸게"가 몰래 "똑똑하게"로 바뀐 요청이 들어옵니다. 형식은 정상이라 서버는 구분할 수 없고, 비싼 모델이 골라져 결제됩니다.

### 막는 기준: 구매자의 한 건 예산 (설정값)

이 프로젝트는 "구매자 지갑 하나 = 사용자 한 명"입니다. 그래서 사용자마다 예산을 등록받지 않고, **구매자의 한 건 예산을 agent-M2M 설정값으로 미리 정해 둡니다.**

| 설정값 | 기본값 | 뜻 |
| --- | --- | --- |
| `AEGIS_BUYER_BUDGET_PER_PAYMENT` | 0.1 (AEGIS) | 구매자 본인의 한 건 예산. **3번 담당이 `.env.example`에 설명과 함께 추가** |

- 비교 기준은 이 설정값입니다. 요청에 같이 오는 `budget`은 해커가 함께 바꿀 수 있으니 **기준으로 쓰지 않습니다.**
- 시나리오 1의 "1건 상한"(`AUDIT_LIMIT_PER_PAYMENT` = 0.5 AEGIS)과는 다릅니다. 1건 상한은 **서비스의 안전장치**, 이 값은 **구매자 본인의 씀씀이**입니다. 그래서 기본값을 1건 상한보다 작게 둡니다.
- 환경변수가 없거나 빈 값이면 **이 규칙은 적용하지 않고 그대로 통과**시킵니다. 알림도 남기지 않습니다.

### 막을 것

| 검사 | 서버 | Solidity | 걸리면 |
| --- | --- | --- | --- |
| 결제 금액 > 구매자 예산 | ✔ 송금 직전 자리 | (선택) ✔ 지갑별 상한 | 결제 거절, 예산과 실제 금액을 이유에 남김 |
| 예산 설정값이 비어 있음 | - | ✘ | 이 규칙은 적용하지 않음. 그대로 통과, 알림도 없음 |

### 쓸 자리

- **서버** `.env.example`: `AEGIS_BUYER_BUDGET_PER_PAYMENT=0.1`을 설명(무엇과 비교하는지, 비우면 규칙을 끈다는 것)과 함께 한 줄 추가합니다.
- **서버** `BEFORE_PAYMENT_CHECKS`: 규칙 파일에서 `AEGIS_BUYER_BUDGET_PER_PAYMENT`를 읽어 `parse_aegis`로 바꾸고, `ctx.decision["winner"]["amountUnits"]`가 이 값을 넘으면 `AuditBlockedError`로 거절합니다. 이유에 예산과 실제 금액을 남깁니다.
- **Solidity** (선택) `BudgetRule`: 지갑별 상한을 두고, **운영자(`owner`)만** 바꿀 수 있게 하세요. 기본값은 서버 설정값과 같게 둡니다. 구매자 지갑 키는 결제 서버에 있어서, 서버가 뚫리면 지갑 주인 권한도 함께 넘어갑니다. 지갑 주인이 바꿀 수 있게 하면 해커가 상한부터 올려 버리므로, 운영자만 바꾸게 해야 서버가 뚫려도 체인에서 한 번 더 막힙니다.
- 예산을 바꾸는 창구는 설정값뿐이라, 예산 등록 API·저장소·사용자 인증은 만들지 않습니다.

### 재현 테스트

- 서버: 설정값을 테스트 데이터의 가장 싼 모델 금액보다 조금 높게 둡니다. 같은 문장을 `priority: "price"`로 보내면 통과하고, `"intelligence"`로 바꿔 보내면(바꿔치기) 막히는지 확인합니다. 테스트 데이터(`tests/fixtures`)에서는 싸게면 "테스트 OpenAI", 똑똑하게면 "테스트 Anthropic"이 골라집니다. 금액은 고정값으로 쓰지 말고 결정 결과에서 읽습니다.
- 서버: 요청의 `budget`을 크게 바꿔 보내도 설정값 기준으로 막히는지 확인합니다.
- 서버: 설정값이 비어 있으면 이 규칙에 걸리지 않고 `SETTLED`로 통과하는지 확인합니다.
- Solidity(선택): 운영자가 정한 상한을 넘는 `pay`는 revert, 운영자가 아닌 지갑이 상한을 바꾸려 하면 revert 되는지 확인합니다.
